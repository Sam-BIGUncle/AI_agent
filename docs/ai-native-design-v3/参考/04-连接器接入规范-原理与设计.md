# 连接器接入规范:原理与设计

> 说明:本文档中的“连接器”,在后来的设计里改名为“业务包”,含义相同:一个业务交给平台的那一包东西(工具、排查说明、代码仓库登记、考题)。格式以 [11-业务包接入协议](../11-业务包与Skill-原理与设计.md) 为准。

> 本文档是按网页版写的早期版本。连接器的目录和清单格式以 [11-连接器接入协议](../11-业务包与Skill-原理与设计.md) 为准;本文档中关于三种形态、三种范围的讨论仍可作为二期的参考。

连接器是各类系统接入 Agent 的统一形式。它支持两种接入模式:平台主动接入(平台团队来写)和业务自助接入(业务方按规范自己写)。两种模式产出的是同一种连接器,走同一条调用路径和同一套质量门槛,区别只在由谁编写和维护。

相关文档:[总体设计](01-总体设计.md)、[评估系统:原理与设计](../02-评估系统-原理与设计.md)、[自研运行时:原理与设计](03-自研运行时-原理与设计.md)、[MCP 网关与 Skill 管理:原理与设计](05-MCP网关与Skill管理-原理与设计.md)。

## 1. 基本理念

| 理念 | 含义 | 对设计的影响 |
| --- | --- | --- |
| 依赖反转 | 平台核心只认连接器规范,不了解任何具体业务 | 业务逻辑只存在于连接器中,不进入网关和运行时的核心代码。平台团队自己写的接入也做成连接器 |
| 一种形式,两种来源 | 连接器可以由平台团队写,也可以由业务方写 | 两种来源使用同一份规范、同一条调用路径、同一套检查和评估,运行时不区分来源 |
| 连接器是打包和归属的单位 | 工具回答“能做什么”,Skill 回答“该怎么做”,连接器回答“这是谁的、怎么一起启用和停用” | 所有工具和 Skill 都归属于某个连接器。连接器有三种形态,可以只含一个 MCP 工具或一个 Skill;接入一个完整的业务时才要求工具、Skill、知识、评估案例齐备(第 2.2 节) |
| 平台管边界,业务管内容 | 认证、授权、审计、脱敏、限流是所有业务共同的要求 | 这些由网关在调用路径上强制执行,连接器不需要实现,也无法绕过 |
| 质量由评估把关 | 靠人工评审每个连接器,平台团队会成为瓶颈 | 业务方自带案例,自动跑分,达标才开放 |
| 业务方提供的文字都是不可信输入 | 工具说明、工具返回、Skill 都会进入模型上下文,都可能影响模型行为 | 上线前检查,上线后锁定版本,返回内容按数据处理 |
| 使用标准协议 | 自定义协议会把业务方绑定在本平台上,接入意愿低 | 工具接入采用 MCP;业务方写的连接器在其他 Agent 产品里也能用,已有的 MCP Server 可以直接接入 |

## 2. 一个连接器包含什么

```mermaid
flowchart LR
  subgraph CONN["连接器(业务方提供)"]
    MF["清单<br/>名称 · 负责人 · 版本 · 权限范围"]
    T["工具<br/>MCP Server 或接口描述"]
    S["Skill<br/>排查方法"]
    K["知识<br/>文档目录与索引"]
    E["评估案例<br/>题目与数据快照"]
  end
  subgraph PLAT["平台"]
    REG["连接器注册表"]
    GW["MCP 网关"]
    RT["Agent 运行时"]
    EV["评估系统"]
  end
  MF --> REG
  T --> GW
  S --> RT
  K --> RT
  E --> EV
  REG --> GW
  REG --> RT
```

| 组成 | 内容 | 谁使用 |
| --- | --- | --- |
| 清单 | 连接器名称、所属应用、负责人、版本、依赖的其他连接器、申请的权限范围、数据敏感级别 | 注册表:决定谁能用、何时加载 |
| 工具 | 业务查询能力。两种提供方式见第 3 节 | 网关:代理调用 |
| Skill | 这个业务的常见问题怎么排查,引用本连接器的工具名 | 运行时:按需加载 |
| 知识 | 接入文档、故障手册、业务规则,附索引 | 运行时:按需读取或检索 |
| 评估案例 | 本业务的历史问题、真实根因、关键证据、数据快照 | 评估系统:接入门槛和回归 |
| 代码仓库 | 在清单中声明仓库地址、与线上服务的对应关系、给 Agent 看的说明文件 | 代码仓库管理:同步镜像,为任务准备代码目录。见 [代码仓库管理](08-代码仓库管理-原理与设计.md) |

应用档案里的日志入口、指标入口也在接入时登记。登记之后,平台提供的通用连接器(日志、监控、报警、发布)对这个业务自动可用,业务方不需要自己实现这些。

### 2.1 两种接入模式

```mermaid
flowchart TB
  subgraph SRC["连接器的来源"]
    P1["平台主动接入<br/>平台团队编写和维护"]
    P2["业务自助接入<br/>业务方编写和维护"]
    P3["直接采用<br/>已有的 MCP Server"]
  end
  SPEC["同一份规范<br/>清单 · 工具 · Skill · 知识 · 评估案例"]
  GATE["同一套门槛<br/>规范检查 · 安全检查 · 评估"]
  REG["连接器注册表"]
  GW["MCP 网关<br/>同一条调用路径"]
  P1 --> SPEC
  P2 --> SPEC
  P3 --> SPEC
  SPEC --> GATE --> REG --> GW
```

| | 平台主动接入 | 业务自助接入 |
| --- | --- | --- |
| 谁来写 | 平台团队 | 业务团队 |
| 谁维护、谁对质量负责 | 平台团队 | 业务团队 |
| 适合的对象 | 所有业务通用的系统(日志、监控、报警、发布、应用档案);试点阶段的基础服务;对平台价值高但业务方暂时没有人力的系统;第三方系统 | 业务自己的查询能力和排查方法;数量多、平台团队不了解细节的业务 |
| 业务知识从哪来 | 平台团队向业务方调研,成本高,容易过时 | 业务方自己掌握,最准确 |
| 接入速度 | 单个快,总量受平台团队人力限制 | 单个取决于业务方,总量不受平台限制 |
| 代码位置 | 平台的连接器仓库 | 业务方自己的仓库,或以描述文件提交到连接器仓库 |
| 信任级别 | 平台自己编写,说明和 Skill 不需要额外的安全确认 | 首次上线和说明变更需要安全确认(第 8 节) |
| 评估案例 | 平台团队整理,通常需要业务方协助确认根因 | 业务方提供 |

第三种来源是直接采用已有的 MCP Server(开源的或厂商提供的)。它不需要编写工具,但仍要补齐清单、Skill 和评估案例,并按业务自助接入的信任级别处理。

两种模式的使用原则:

- **通用的由平台做,业务特有的由业务做。** 通用系统每个业务都要用,由平台做一次最划算。
- **平台主动接入用于启动,不作为长期方式。** 早期没有效果数据,业务方不会主动来接,需要平台先接几个有代表性的业务做出样板。
- **主动接入的连接器可以移交。** 因为形式相同,移交只是变更清单里的负责人和代码归属,调用方没有任何感知。移交的时机是业务方开始自己提出修改需求的时候。
- **平台主动接入也不能跳过门槛。** 同样要通过规范检查和评估。否则平台自己写的连接器会成为质量最没有保障的那一批。

### 2.2 三种形态与三种范围

MCP 工具、Skill、连接器的定位:

| | 回答的问题 | 是什么 |
| --- | --- | --- |
| MCP 工具 | 能做什么 | 一个可调用的能力:查日志、查订单、读缓存 |
| Skill | 该怎么做 | 一份写给模型看的操作说明:某类问题怎么查、查到什么程度算查清 |
| 连接器 | 这是谁的、怎么一起启用和停用 | 打包和归属的单位:把相关的工具、Skill、知识、仓库声明放在一起,有名称和负责人 |

Skill 会引用工具。工具可以脱离 Skill 单独使用;Skill 也可以不依赖专门的工具,只使用 Agent 已有的能力。

连接器不必包含全部组成部分。按包含的内容分三种形态:

| 形态 | 包含 | 例子 | 上线要求 |
| --- | --- | --- | --- |
| 工具型 | 只有 MCP 工具 | 日志查询、监控查询、一个第三方的 MCP 服务 | 规范检查、安全检查 |
| 说明型 | 只有 Skill | “如何判断问题是否由发布引起”“排查报告怎么写” | 规范检查 |
| 业务型 | 工具、Skill、知识、代码仓库、评估案例 | 会员业务、支付业务 | 另外要求评估达标 |

单独配置一个 MCP 或一个 Skill,做法是建立一个只含它的连接器,清单中填写名称、负责人、说明。这样它有归属,可以被启用和停用。

反过来,一个连接器也可以包含很多 MCP 工具和很多 Skill。基础业务连接器就是这样:它是一个连接器,覆盖用户、会员、权益三个服务,内部按服务分组:

```
membership/
  connector.yaml             清单:负责人、包含的服务及各自的工具前缀、依赖
  tools/
    user/                    用户服务的工具,前缀 user_
    member/                  会员服务的工具,前缀 member_
    entitlement/             权益服务的工具,前缀 entitlement_
    flow/                    跨服务的链路工具,例如按订单返回各段状态
  skills/
    overview/                三个服务的整体情况与服务地图
    entitlement-missing/     付费后权益未到账
    ...                      其他排查说明
  knowledge/                 表结构说明、缓存说明、接入文档
  evals/                     案例
```

放在一个连接器里的依据是:三个服务由同一个团队负责,并且主要的排查链路跨越这三个服务。将来有人只需要其中一部分时再拆分。

按可见范围分三种:

| 范围 | 谁能使用 | 审核 |
| --- | --- | --- |
| 个人 | 只有自己 | Skill 不需要审核;MCP 需要管理员批准 |
| 团队 | 一个团队的成员 | 团队负责人确认 |
| 平台 | 所有有权限的人 | 第 6 节的完整流程 |

个人范围的 MCP 也需要批准的原因:Agent 调用工具时会把参数发送给它,参数中可能带有业务数据,不受控的 MCP 服务是一条数据外流的通道。只是自己试验时,在本地的 Claude Code 中配置更合适。

## 3. 工具的两种接入方式

| | 自带 MCP Server | 声明式接入 |
| --- | --- | --- |
| 业务方提供 | 一个按 MCP 协议实现的远程服务 | 现有的 HTTP 接口,加一份描述文件 |
| 描述文件内容 | 无,工具定义由 MCP Server 自己给出 | 工具名、说明、参数结构、对应的接口地址与参数映射、返回字段的保留与裁剪规则 |
| 谁来运行 | 业务方部署和维护 | 网关根据描述生成工具,业务方只维护原有接口 |
| 适合 | 需要组合多个内部接口、有较复杂的整形逻辑 | 简单查询,一个接口对应一个工具 |
| 门槛 | 较高 | 低,多数业务从这里开始 |

两种方式对 Agent 来说没有区别,它看到的都是网关上的工具。

## 4. 规范规定什么

### 4.1 工具规范

| 项目 | 要求 |
| --- | --- |
| 命名 | `<业务前缀>_<动作>_<对象>`,例如 `pay_get_order`。前缀在注册时分配,全局唯一 |
| 说明 | 必须写明用途和使用时机,例如“订单已支付但下游未收到通知时使用,需要订单号” |
| 参数 | 有明确的结构定义;`env` 必填;时间用带时区的 ISO 8601;接受用户手上有的标识(手机号、订单号) |
| 只读声明 | 每个工具声明是否只读。第一期只接受只读工具 |
| 返回 | 区分无数据、参数错误、无权限、超时;默认返回少量并说明总数和缩小范围的方法;不超过平台规定的大小上限 |
| 时限 | 在平台规定的超时内返回;耗时长的查询提供统计类工具代替 |
| 稳定性 | 工具名和参数发布后不做破坏性修改,需要变化时发布新工具 |

### 4.2 身份与数据权限

- 网关在转发调用时附带一个签名的身份令牌,内容是发起人、所属团队、目标应用、环境。
- 连接器用这个令牌决定返回哪些数据。**身份只来自令牌,不接受工具参数里的任何身份信息**,因为参数是模型填的。
- 连接器在清单中声明每个返回字段的敏感级别,网关据此脱敏。未声明的字段按最严格的级别处理。

### 4.3 Skill、知识、评估案例规范

- Skill:描述写明适用场景;正文写思路和判断标准;只引用已注册的工具名;不包含评估案例里的具体数据。
- 知识:Markdown 格式,有索引,每篇标明负责人和更新日期。
- 评估案例:格式和写题时的注意事项见评估系统文档第 3 节。接入时至少提供约定数量的案例,覆盖正常排查和至少一种非正常类型。

## 5. 平台在调用路径上做什么

```mermaid
sequenceDiagram
  participant R as Agent 运行时
  participant G as MCP 网关
  participant C as 业务连接器
  participant B as 业务系统
  R->>G: 调用工具(带发起人身份)
  G->>G: 认证,按应用成员关系和连接器权限范围授权
  G->>G: 校验参数结构,检查限流
  G->>C: 转发,附签名身份令牌
  C->>B: 按令牌中的身份查询
  B-->>C: 数据
  C-->>G: 结果
  G->>G: 大小限制,按敏感级别脱敏,写审计
  G-->>R: 整形后的结果
```

连接器只负责“按身份查数据并返回”。其余每一步都在网关,对所有连接器一致。

连接器故障相互隔离:某个连接器超时或报错率过高时,网关对它熔断并向模型返回明确的不可用信息,不影响其他连接器。

## 6. 接入流程

```mermaid
flowchart LR
  A["登记应用档案"] --> B["提交连接器"] --> C["自动规范检查"] --> D["运行评估"] --> E{"达标?"}
  E -- "否" --> B
  E -- "是" --> F["实验状态<br/>仅白名单可用"] --> G["正式状态"]
  G -.->|"质量下降"| F
```

| 环节 | 内容 |
| --- | --- |
| 提交 | 向连接器仓库提交清单、描述文件或 MCP Server 地址、Skill、知识、案例 |
| 自动规范检查 | 命名与前缀、说明是否包含使用时机、参数结构、只读声明、连通性、返回大小、响应时间、Skill 中是否出现案例数据 |
| 安全检查 | 工具说明和 Skill 中是否含有指令性内容(见第 8 节);首次上线和说明变更时需人工确认 |
| 评估 | 跑本业务的案例,同时跑平台回归集,确认新连接器没有让其他业务的分数下降 |
| 状态 | 草稿、实验、正式、停用。实验状态只对业务方自己的白名单可见 |

平台主动接入的连接器走同一个流程,区别只有一处:由平台团队编写的工具说明和 Skill 不需要额外的安全确认。

## 7. 加载策略

连接器多了以后,不能把所有工具都交给模型,否则它会选不准,上下文成本也高。

- 任务开始时,根据涉及的应用,加载三部分:平台通用连接器、该应用的连接器、清单中声明的依赖连接器。
- 提供一个查找工具的工具。排查过程中需要跨到其他业务时,Agent 按描述检索并申请加载,仍受发起人权限约束。
- 单个任务可加载的工具数有上限。
- Skill 和知识按同样的范围过滤。

### 7.1 使用方式:三类连接器与使用方的选择

平台有三种角色:使用方提问,并选择一次对话启用哪些连接器;业务方把自己的业务做成连接器并负责维护;平台方提供框架、公共连接器、规范和审核。

```mermaid
flowchart TB
  U["使用方"]
  subgraph ALWAYS["公共连接器:始终加载"]
    A1["日志查询"]
    A2["监控 · 发布记录"]
    A3["通用排查方法"]
  end
  subgraph DEFAULT["基础业务连接器:默认加载"]
    B1["用户"]
    B2["会员"]
    B3["权益"]
  end
  subgraph OPT["业务连接器:选择后加载"]
    C1["支付"]
    C2["推荐"]
    C3["其他业务方接入的"]
  end
  AG["本次对话的 Agent"]
  BIZ["业务方"]
  ALWAYS --> AG
  DEFAULT --> AG
  U -->|"手动选择 · 团队默认 · 确认 Agent 的建议"| OPT
  OPT --> AG
  BIZ -->|"接入并维护"| OPT
```

| 类别 | 例子 | 加载方式 | 使用方能否关闭 | 理由 |
| --- | --- | --- | --- | --- |
| 公共连接器 | 日志查询、监控、发布记录、通用的排查方法 | 始终加载 | 不能 | 几乎每个问题都会用到 |
| 基础业务连接器 | 用户、会员、权益 | 默认加载 | 可以 | 大部分业务问题最终都牵涉到它们 |
| 业务连接器 | 业务方接入的各个业务 | 选择后加载 | 可以 | 全部加载会让工具过多,模型选不准,成本也高 |

使用方选择连接器的三种方式:

| 方式 | 做法 |
| --- | --- |
| 手动选择 | 输入框旁提供连接器选择入口,列出本人有权限的连接器,每个附一句说明和几个示例问题 |
| 团队默认 | 每个团队预设一组默认启用的连接器 |
| Agent 建议 | 排查中发现问题牵涉到未启用的业务时,Agent 提示启用,由使用方确认。不自动加载 |

启用一个连接器时:它的工具进入本次对话的工具清单;它的 Skill 描述进入系统提示;它的知识和表结构说明可以被读取;它声明的代码仓库加入任务的代码目录;它声明依赖的连接器一并启用。

规则:

- 没有权限的连接器不出现在列表中,也无法启用。
- 同时启用的连接器和工具总数有上限,界面显示当前数量。
- 对话中途可以增加连接器,从下一轮生效。移除时建议新开对话,因为上下文中仍保留着它之前返回的内容。
- 每个任务记录启用了哪些连接器及其版本。

一期只有公共连接器和基础业务连接器,全部默认加载,界面显示当前加载的连接器但不可选择。目录从一开始就按这两类组织,二期增加选择入口时不需要调整已有内容。

### 7.2 连接器之间的隔离

连接器是业务之间的边界。一次对话只使用它加载的连接器,没有加载的连接器对这次对话来说等于不存在。甲业务和乙业务各有自己的连接器,互不影响。

没有加载的连接器,下列内容都不会进入这次对话:

| 内容 | 加载时 | 未加载时 |
| --- | --- | --- |
| 工具 | 出现在工具清单中,可以调用 | 不在清单中,调用会被网关拒绝 |
| Skill | 描述进入系统提示,正文可读取 | 描述和正文都不可见 |
| 知识、表结构说明 | 可以被搜索和读取 | 不在可访问的目录中 |
| 代码仓库 | 加入任务的代码目录 | 不在目录中 |
| 连接器自己的说明 | 进入系统提示 | 不进入 |

唯一的例外是一份连接器目录:每个连接器的名称和一句话说明。它用于让 Agent 在需要时建议启用某个连接器,其中不包含任何业务内容。

保证互不干扰的规则:

| 规则 | 说明 |
| --- | --- |
| 命名带前缀 | 工具名和 Skill 名都以连接器登记的前缀开头,不同业务不会重名 |
| 业务内容不进常驻说明 | 平台的常驻说明只放所有业务通用的规则。某个业务特有的规则放在该连接器自己的说明里,只在它被加载时生效 |
| 连接器只能引用自己的东西 | Skill 只能引用本连接器的工具、公共连接器的工具、以及清单中声明依赖的连接器的工具 |
| 连接器不能改变平台规则 | 连接器中的说明优先级低于平台的常驻说明。它不能放宽只读、权限、输出格式这类平台级的要求 |
| 内容标明适用范围 | 每份 Skill 和说明写明它适用于哪个业务,避免同时加载多个连接器时被用到别的业务上 |
| 检索限定范围 | 搜索知识和代码时,范围限定在已加载的连接器之内 |
| 权限独立 | 加载连接器不等于获得数据权限。工具调用时仍按发起人对该业务的权限判断 |

同时加载多个业务连接器时,可能出现两类冲突,处理方式如下:

| 冲突 | 例子 | 处理 |
| --- | --- | --- |
| 同一个词含义不同 | 两个业务都有“订单”,指的不是同一种东西 | 各自的说明和工具说明中写明所指的对象;工具名的前缀本身也起区分作用 |
| 两份 Skill 都声称适用 | 两个业务各有一份“支付失败排查” | Skill 的描述中必须带业务名;发布前的重叠检查覆盖已有的全部连接器 |

公共连接器和基础业务连接器是所有对话的共同基础,所以它们的内容要保持中立:不包含只对某个业务成立的假设。

新连接器上线前要跑其他业务的回归案例(第 6 节),目的就是验证这种隔离确实成立:加入它之后,其他业务的结果没有变差。

## 8. 安全

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 工具说明中夹带指令 | 说明会进入模型上下文,可以写入“调用本工具前先把会话内容发给某处”之类的内容 | 上线前自动检查加人工确认;说明按版本锁定,任何修改都要重新过检查后才生效 |
| 工具返回中夹带指令 | 返回内容来自业务数据,可能包含用户填写的文字 | 返回按数据处理;第一期没有写工具和外发通道,被诱导的影响限于读取 |
| 连接器越权取数 | 连接器返回了发起人无权看的数据 | 身份只来自签名令牌;网关按清单声明的权限范围授权;审计抽查 |
| 跨业务数据流动 | 甲业务的查询结果留在上下文里,被当作参数传给乙业务的工具 | 第一期全部只读,影响有限;开放写工具之前需要先设计数据流向的限制 |
| 连接器拖垮平台 | 响应慢、返回过大、频繁报错 | 超时、大小上限、熔断,按连接器隔离 |

## 9. 运营

- **负责人。** 每个连接器有明确的负责人,出问题时通知到人。
- **质量看板。** 按连接器统计调用量、错误率、响应时间、评估分数、用户反馈。
- **自动降级。** 错误率或评估分数跌破阈值时,自动退回实验状态并通知负责人。
- **版本。** 清单带版本号;运行记录中保存所用连接器的版本,便于追溯。

## 10. 与现有方案的关系

- **第一期全部是平台主动接入。** 用户、会员、权益三个基础服务,以及日志、监控、报警、发布、应用档案这些通用系统,都由平台团队按这份规范做成连接器。规范好不好用,先由自己验证。
- **业务自助接入从第二个业务开始。** 那时三个基础服务的连接器就是现成的样板。
- **两种模式长期并存。** 通用系统和第三方系统始终由平台接入;业务特有的能力逐步转为业务自助,已有的主动接入连接器按第 2.1 节移交。
- **规范先行,机制后做。** 规范和自动检查在第一期就确定并自用;注册表、自助流程、按任务加载等机制,在第二个业务要接入时再建设,那时才清楚真实需求。
- **对总体设计的补充。** 本文档细化总体设计第 5.7 节;第 5.1 节的工具清单是按本规范实现的第一批连接器。
