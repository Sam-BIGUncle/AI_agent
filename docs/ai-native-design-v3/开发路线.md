# 开发路线

本文档回答三个问题:平台拆成哪几个可以独立开发的模块;模块之间靠什么约定连接;按什么顺序做、在哪几个点上合起来跑整体流程。

总纲见 [架构总览](架构总览.md),范围见 [一期二期规划](一期二期规划.md),模块之间传递的数据见 [数据定义](13-数据定义-原理与设计.md)。

## 1. 十二个模块

拆分的原则:每个模块有明确的输入和输出,可以单独开发、单独验收;模块之间只通过第 2 节的约定打交道。

| # | 模块 | 是什么 | 设计 |
| --- | --- | --- | --- |
| 1 | 网关核心 | 一次调用的流水线:认人、限流、查有效权限、审计、转发、出口兜底;连接时生成工具列表和服务说明;对 MCP 服务的并发控制和熔断 | 文档 15 |
| 2 | 插件 | 全平台唯一的插件:网关地址、入口说明、安装说明 | 文档 09 第 3、4、6 节 |
| 3 | 登录授权 | OAuth 授权页接公司 SSO,发通行证 | 文档 09 第 5 节 |
| 4 | 权限管理 | 授权表、有效权限的计算、管理页面(用户、用户组、授权、反查、判断解释、修改记录) | 文档 12 |
| 5 | MCP 接入与工具库 | MCP 服务的登记、刷新发现、工具库、批准 | 文档 16 第 1 至 5 节 |
| 6 | 通用查询服务 | 平台代接用:在后台配查询就生成工具 | 文档 16 第 6 节 |
| 7 | 业务包管理 | 业务包和 Skill 的编辑、自动检查、跑考题、发布、回滚、停用;生成登记表 | 文档 11 |
| 8 | 平台的 MCP 服务 | 查日志、发布记录、Skill 下发、提交反馈 | 文档 11 第 6 节;文档 09 第 7 节 |
| 9 | 代码服务 | 仓库同步、按版本的快照、搜索和读取 | 文档 10 |
| 10 | 接入 SDK | Go 版本,包装官方 MCP SDK | 文档 16 第 7 节 |
| 11 | 第一批业务接入 | 用户、会员、权益:大部分工具由通用查询服务代接,权益服务用 SDK 自助;公共包和基础业务包的内容 | 文档 11、16 |
| 12 | 评估 | 批量提问脚本、结果表、汇总 | 文档 02 |

另有一项横向的工作,从模块 1 开始就一起做:部署配置、指标、日志、告警(文档 14)。

| 类别 | 模块 | 特点 |
| --- | --- | --- |
| 架子 | 1、3、4、5、7 | 只做一次,不出现任何业务名词 |
| 平台的 MCP 服务 | 6、8、9 | 只做一次;对网关来说和业务的服务没有区别 |
| 给业务用的工具 | 2、10 | 几乎不变 |
| 内容 | 11 | 每接一个业务做一份。以后新业务接入,只做这一块 |
| 衡量 | 12 | 之后所有改进都靠它 |

### 1.1 几个容易混的边界

| 问题 | 答案 |
| --- | --- |
| 网关会执行查询吗 | 不会。网关只转发。查询由通用查询服务或业务的 MCP 服务执行 |
| 模块 5 和模块 7 的区别 | 模块 5 管“有哪些工具、批准了没有”;模块 7 管“一个业务包选了哪些工具、配了哪些 Skill” |
| 模块 4 和模块 7 的区别 | 模块 7 决定业务包里有什么;模块 4 决定谁能用这个业务包 |
| 通用查询服务和业务的 MCP 服务有什么区别 | 对网关没有区别,都是登记过的 MCP 服务。区别只在谁运行它 |
| Skill 下发为什么是一个 MCP 服务 | 同事取 Skill 也要经过登录和权限,做成 MCP 服务就自动走同一条流水线 |

## 2. 模块之间的约定

模块能独立开发,靠的是先把它们之间的约定定下来。约定的数据结构都在文档 13 里。

| # | 约定 | 谁提供 | 谁使用 | 定义在 |
| --- | --- | --- | --- | --- |
| ① | MCP 协议 | 网关;各 MCP 服务 | Claude Code;网关 | 公开标准 |
| ② | 身份 | 模块 3 | 模块 1 | 文档 13 第 8 节 |
| ③ | 有效权限 | 模块 4 | 模块 1 | 文档 13 第 9 节 |
| ④ | 登记表 | 模块 7 | 模块 1、4、8 | 文档 13 第 7 节 |
| ⑤ | 转发和结果的约定 | 模块 1 | 模块 6、8、9、10 和业务的服务 | 文档 13 第 10 节 |
| ⑥ | MCP 服务登记和工具 | 模块 5 | 模块 4、7 | 文档 13 第 2、3 节 |
| ⑦ | 业务包和 Skill | 模块 7 | 模块 4、8 | 文档 13 第 4、5 节 |
| ⑧ | 授权 | 模块 4 | 模块 4 自己 | 文档 13 第 6 节 |
| ⑨ | 命令行提问 | Claude Code | 模块 12 | 文档 02 |

每种结构都带版本号,升级时只加字段。要改约定,先改文档 13。

每个模块独立测试时,用什么代替对方:

| 模块 | 用什么代替对方 |
| --- | --- |
| 1 网关核心 | 固定的假身份;手写的有效权限;手写的登记表;一个原样返回参数的小 MCP 服务 |
| 2 插件 | 模块 1 的假工具版本 |
| 3 登录授权 | 一个不带工具的空 MCP 服务 |
| 4 权限管理 | 手写的登记表;手工建几个测试用户;直接调判断接口 |
| 5 MCP 接入与工具库 | 一个可以随时改工具定义的测试 MCP 服务 |
| 6 通用查询服务 | 一个测试数据库 |
| 7 业务包管理 | 手工登记的几个工具 |
| 8 平台的 MCP 服务 | 测试的日志表;几份样例 Skill |
| 9 代码服务 | 一个公开的小仓库 |
| 10 接入 SDK | 一个示例服务 |
| 11 第一批业务接入 | 模块 7 的自动检查 |
| 12 评估 | 不装插件的 Claude Code 加两道无关的题 |

## 3. 执行顺序和三个合流点

```mermaid
flowchart LR
  S0["阶段 0<br/>验证"] --> A1["1 网关"] --> A2["2 插件"] --> J1{{"合流点一<br/>链路通"}}
  J1 --> A3["3 登录"] --> A5["5 MCP 接入"] --> A6["6 通用查询"] --> A4["4 权限"] --> A7["7 业务包"] --> A8["8 平台 MCP"] --> J2{{"合流点二<br/>架子通"}}
  J2 --> A10["10 SDK"] --> A11["11 第一批业务"] --> J3{{"合流点三<br/>业务通"}}
  J3 --> A9["9 代码服务"] --> A12["12 评估"] --> ALL["整体流程<br/>改进 · 上线 · 试用"]
```

| 顺序 | 模块 | 为什么排在这里 | 这个模块自己的验收 |
| --- | --- | --- | --- |
| 0 | 阶段 0 验证 | 先排除最大的不确定性(第 4 节) | 结果表填完 |
| 1 | 网关核心 | 其他模块都挂在它上面 | 文档 15 第 8 节 |
| 2 | 插件 | 很小,做完就能看到第一个效果 | 一台干净的电脑按说明装好 |
| | **合流点一:链路通** | | 在 Claude Code 里问一句话,它调用了网关后面的假工具 |
| 3 | 登录授权 | 换掉假身份 | 浏览器登录一次后可用;未登录和过期的请求被拒绝 |
| 5 | MCP 接入与工具库 | 有了它才有真的工具 | 登记一个测试服务,刷新后工具进入待批准;批准后可用;改了只读变读写后回到待批准 |
| 6 | 通用查询服务 | 第一个真正提供数据的服务 | 配一条查询生成工具,能查到测试库;超时和超行数被拦下;参数改不了语句结构;打码生效;四种结果能区分 |
| 4 | 权限管理 | 换掉手写的有效权限 | 文档 12 第 12 节 |
| 7 | 业务包管理 | 把工具和 Skill 组合起来 | 建一个业务包,选工具、写 Skill、发布;自动检查能拦下引用了包外工具的 Skill;回滚后网关用回旧内容 |
| 8 | 平台的 MCP 服务 | Skill 要靠它送到同事 | 能按名称取到 Skill 正文和附件;能查到真实日志 |
| | **合流点二:架子通** | | 一个样例业务包:一条通用查询工具加一份 Skill。授权后,同事在 Claude Code 里能按 Skill 查到数据;在授权里排除这个 MCP 后,同一个人查不到了。全程不改网关代码 |
| 10 | 接入 SDK | 第一批业务里有一个服务要用它 | 用 SDK 写的示例服务,登记后工具能被发现、调用,四种结果正确,非网关的请求被拒绝 |
| 11 | 第一批业务接入 | 架子好了才装内容 | 两个业务包通过自动检查;考题齐全 |
| | **合流点三:业务通** | | “付费后权益未到账”能沿链路给出带证据的结论;信息不够时先问;客服组的人用不了被排除的服务 |
| 9 | 代码服务 | 独立性最强,放在后面不挡路 | 文档 10 第 8 节 |
| 12 | 评估 | 之后所有改进都靠它 | 一条命令跑完全部考题,生成结果表 |
| | **整体流程** | | 至少三轮“看错题、改一样、重跑”;文档 14 第 8 节的上线前清单;两三位同事试用;一期评审 |

**为什么合流分三次。** 每个模块有自己的验收,用假的对方测试;但模块之间的约定写在纸上时总有没想到的地方,越晚发现改动越大。三个合流点各只需要半天。

**可以并行的部分。** 约定定下后,模块 3、4、5、6、9、10 可以同时开发。模块 11 里的文字部分(服务地图、Skill、表结构说明、考题)从今天就可以开始写。

**模块 11 里最花时间的是内容,不是代码。** 服务地图、状态字段的含义、排查思路,只有懂业务的人能写。

**检验架子的办法。** 合流点三之后,再接一个很小的假业务:登记一个服务、建一个业务包、授权。平台代码一行不改就能接上,说明架子是对的。

**和规划的对应。** 合流点一、二对应 [一期二期规划](一期二期规划.md) 的 M1,合流点三和模块 9 对应 M2,模块 12 和改进对应 M3,上线和试用对应 M4,评审对应 M5。

## 4. 阶段 0:验证

这几项是方案里不确定性最大的地方。大部分不需要先写平台代码。

| # | 不确定的是什么 | 怎么测 | 不通过怎么办 |
| --- | --- | --- | --- |
| 1 | 登录:Claude Code 的插件能不能对接平台的 OAuth 页 | 一个不带工具的空 MCP 服务,加上 OAuth 页。看能否弹出浏览器、登录成功、过期后自动续期。顺便试一次 `claude -p` 加应用凭据 | 调整客户端登记方式 |
| 2 | 数据:三个服务的日志和数据能不能关联起来 | 取 3 个真实的“付费后权益未到账”,自己写 SQL 把整条链路查出来 | 人都串不起来,Agent 也做不到。先在服务里补日志字段 |
| 3 | 版本:能不能拿到线上运行的提交号 | 询问发布系统的负责人,或调用它的接口 | 先人工维护一张表 |
| 4 | 代码:只靠搜索和读取,能不能找到业务逻辑 | 分两步,见第 4.1 节 | 加强导航;仍不行再考虑搜索引擎 |
| 5 | 多副本:网关两个副本时 Claude Code 的连接是否正常 | 第 1 项的空服务起两个副本,不做会话保持;看连接、调用,以及“工具列表变了”的通知 | 网关做成每个请求都能独立处理;通知到不了时以“下次连接生效”为保底 |
| 6 | Skill 放在服务器上,模型会不会主动去取 | 同一批 Skill,同样 10 种问法测两组:放在插件里;放在服务器上要调工具去取 | 改服务说明里的目录和入口说明;仍不行就切到“发布到插件里” |
| 7(可选) | 开源方案能不能直接用 | 用一个假的 MCP 服务,在 Obot 或 Nacos + Higress 上走一遍登记、授权、调用,每个限时三天 | 不影响主线,只作为参考 |

### 4.1 代码查询的两步测试

**第一步,不写代码。** 把三个仓库克隆到本机,在 Claude Code 里问 10 个业务逻辑问题。这是效果的上限。再加一份导航文件问一遍,差距就是导航的价值。

**第二步,写一个一次性的小工具。** 只有搜索和读取两个工具的 MCP 服务,直接在本机目录上做文本搜索。把本地仓库移走,同样 10 道题再问一遍。和第一步的差距就是“远程”的代价。

每道题记四样:答对了吗;找到关键代码了吗;搜索和读取各几次;用了多久。

## 5. 每个模块内部的节奏

```mermaid
flowchart LR
  A["读这个模块的设计"] --> B["提意见,定下来"] --> C["交给编码工具实现"] --> D["按验收项检查"] --> E["记下意见"]
  D -- "不符合" --> C
```

交给编码工具时,一次只给一个模块:它的设计文档、文档 13 里它用到的结构,以及 [一期二期规划](一期二期规划.md) 第 2.2 节的“不做”清单。把整个方向一次交出去,范围会越写越大。

安全相关的代码(登录、权限判断、网关转发、通用查询服务的参数处理)要逐行看懂,并且有测试。

## 6. 最容易走偏的地方

| 走偏 | 后果 | 怎么避免 |
| --- | --- | --- |
| 跳过阶段 0 直接开发 | 登录不通或数据串不起来时,后面做的都要返工 | 结果表填完再开始模块 1 |
| 不按约定各做各的 | 合流时对不上 | 模块之间只按文档 13 的结构打交道 |
| 一期做得太厚 | 迟迟答不出第一个真实问题 | 按 [一期二期规划](一期二期规划.md) 第 2.2 节,流程先手工 |
| 网关里混进业务逻辑 | 每接一个业务都要改网关 | 查询只在 MCP 服务里;网关代码里不出现业务名词 |
| 做完评估就直接给人用 | 能跑但答不好,同事用一次就不再用 | 试用之前至少完成三轮改进 |
