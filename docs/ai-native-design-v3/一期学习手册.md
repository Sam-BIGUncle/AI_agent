# 一期学习手册

这本手册按 [开发路线](开发路线.md) 的十二个模块组织。每个模块告诉你三件事:先读什么;要弄懂什么;评审实现时看什么。原理和完整的验收项写在各模块的设计文档里,这里只给出指向,避免两处说法不一致。

每个模块末尾留有“我的意见”。一期结束时,这些意见就是二期的输入。

## 怎么使用

```mermaid
flowchart LR
  A["学:读指定的章节"] --> B["自测:回答文档末尾的问题"] --> C["实现:把章节交给编码工具"] --> D["评审:对照验收项检查"] --> E["记录:写下意见"]
  B -- "答不上来" --> A
  D -- "不符合" --> C
```

交给编码工具时,一次只给一个模块:它的设计文档、[数据定义](13-数据定义-原理与设计.md) 里它用到的部分,以及 [一期二期规划](一期二期规划.md) 第 2.2 节的“不做”清单。

## 准备 A:五个基本概念和 Agent 循环

**先读。** [从这里开始](00-从这里开始.md) 第 1 节。想深入时读 `参考` 目录里《自研运行时》第 1 至 3 节。

**要弄懂。**

- 模型不记事,也不能自己做任何操作。它只能输出“我想调用某个工具,参数是这些”。
- 循环是一段反复执行的程序:把问题交给模型,模型要调用工具就去调用,把结果再交给模型,直到给出答案。一期里这个循环就是同事本地的 Claude Code。
- 模型只知道上下文里有的东西。工具的说明、Skill、服务说明,都是上下文的一部分。
- 工具出错时,错误信息要作为结果交给模型,它才能改参数或换一条路。

**为什么先学这个。** 一期不实现循环,但平台做的每一样东西都是在给这个循环提供工具和上下文。弄懂它,才能判断一份工具说明或 Skill 写得好不好。

**我的意见。**

## 模块 3:登录授权

**先读。** [09-插件形态](09-插件形态-原理与设计.md) 第 5 节;[数据定义](13-数据定义-原理与设计.md) 第 8 节。

**要弄懂。**

## 模块 5:MCP 接入与工具库

**先读。** [16-MCP 接入与工具库](16-MCP接入与工具库-原理与设计.md) 第 1 至 5 节;[数据定义](13-数据定义-原理与设计.md) 第 2、3 节。

**要弄懂。**

## 模块 7:业务包管理

**先读。** [11-业务包与 Skill](11-业务包与Skill-原理与设计.md) 全文;[数据定义](13-数据定义-原理与设计.md) 第 4、5、7 节。

**要弄懂。**

- 业务包里的五样东西,各从哪里来。
- 工具和业务包多对多;Skill 只属于一个业务包,只能引用本包和公共包的工具。
- 编辑的是草稿、同事用的是已发布版本;版本为什么要记工具的定义摘要。

**评审时看。**

- [ ] 建一个业务包,选工具、写 Skill 带附件、填仓库登记、写考题,发布成功
- [ ] Skill 引用了包外的工具时,自动检查拦下
- [ ] 选了未批准的工具时,不能发布
- [ ] 发布后生成新一版登记表;回滚后网关用回旧内容

## 模块 11:第一批业务接入

**先读。** [11-业务包与 Skill](11-业务包与Skill-原理与设计.md) 第 2 至 4 节、第 7 节;[从这里开始](00-从这里开始.md) 第 4 节。

**要弄懂。**

- 同一条信息只写一处:工具用法在工具说明里;一类问题怎么查在 Skill 里;所有任务都遵守的规则在服务说明和入口说明里。
- Skill 写思路和判断标准,不写死步骤;必须写清“查到什么程度才能下结论”。
- 服务地图按业务流程写:每一段靠什么关联、成功的标志是什么。
- “什么时候用”决定 Skill 会不会被取用。

**评审时看。**

- [ ] 两个业务包通过自动检查
- [ ] 每个工具的说明里写了“什么时候用”;查询都带具体标识
- [ ] 服务地图里每一段都写了成功的标志,并且在日志或数据里确实查得到
- [ ] 表结构说明里每个状态字段的取值都有解释
- [ ] Skill 里没有考题中的具体数据
- [ ] 公共包里没有只属于某个业务的内容
- [ ] 权益服务通过 SDK 接入,其余通过通用查询服务代接

**我的意见。**

## 模块 12:评估

**先读。** [02-评估系统](02-评估系统-原理与设计.md) 第一部分;[09-插件形态](09-插件形态-原理与设计.md) 第 5.4 节。

- [ ] 保存了完整过程;任意两次运行可以逐题对比

## 持续:迭代方法

**先读。** [02-评估系统](02-评估系统-原理与设计.md) 第 5 至 8 节。

**要弄懂。** 失败案例比分数重要。每个失败归入一类,不同的类改不同的地方:

| 失败类型 | 改哪里 |
| --- | --- |
| 缺少工具 | 在 MCP 服务里加工具,或在通用查询服务里加一条查询 |
| 选错工具或参数填错 | 工具的名称、说明、参数 |
| 工具返回看不懂或太大 | 工具返回的字段和上限 |
| 找不到资料 | Skill 的附件;仓库的代码导航 |
| Skill 没被取用 | Skill 的“什么时候用”;服务说明里的目录 |
| Skill 指引有误 | Skill 的正文 |
| 证据齐全但推理错误 | Skill 里的判断标准 |
| 过早下结论 | Skill 里“查到什么程度才能下结论” |
| 没有先提问 | 服务说明和入口说明里的规则 |
| 被权限拦住 | 授权的范围是否合理 |

一次只改一样;改动针对一类问题,不针对某一道题;读完整的过程,不只读最终回答;每次改动留一条记录。

**评审时看。**

- [ ] 每个失败都有归类,归类是读过完整过程之后给出的
- [ ] 每轮只改一项,针对占比最大的那类失败
- [ ] 每次改动后重跑了全部考题
- [ ] 有一份持续更新的改动记录

**我的意见。**

## 一期结束时

把各模块的“我的意见”汇总,再加上三项整体意见:

- 对架构的意见:哪些部分实现起来别扭,哪些划分不合理。
- 对安装、登录和使用体验的意见。
- 最想在二期做的事。

这些连同评估数据和试用数据,就是 [一期二期规划](一期二期规划.md) 第 4 节评审的输入。
