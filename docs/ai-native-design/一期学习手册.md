# 一期学习手册

这本手册按 [开发路线](开发路线.md) 的九个模块组织。每个模块告诉你三件事:先读什么;要弄懂什么;评审实现时看什么。原理和验收项都写在各模块的设计文档里,这里不重复,只给出指向,避免两处说法不一致。

每个模块末尾留有“我的意见”。一期结束时,这些意见就是二期的输入。

## 怎么使用

每个模块按同样的五步:

```mermaid
flowchart LR
  A["学:读指定的章节"] --> B["自测:回答文档末尾的问题"] --> C["实现:把章节交给编码工具"] --> D["评审:对照验收项检查"] --> E["记录:写下意见"]
  B -- "答不上来" --> A
  D -- "不符合" --> C
```

交给编码工具时,一次只给一个模块:它的设计文档、[数据定义](13-数据定义-原理与设计.md) 里它用到的部分,以及 [一期二期规划](一期二期规划.md) 第 2.2 节的“不做”清单。

## 准备 A:五个基本概念和 Agent 循环

**先读。** [从这里开始](00-从这里开始.md) 第 1 节。想深入时读 `参考` 目录里的《自研运行时》第 1 至 3 节。

**要弄懂。**

- 模型不记事,也不能自己做任何操作。它只能输出“我想调用某个工具,参数是这些”。
- 循环是一段反复执行的程序:把问题交给模型,模型要调用工具就去调用,把结果再交给模型,直到给出答案。一期里这个循环就是同事本地的 Claude Code。
- 模型只知道上下文里有的东西。工具的说明、排查说明、服务说明,都是上下文的一部分。
- 工具出错时,错误信息要作为结果交给模型,它才能改参数或换一条路。

**为什么先学这个。** 一期不实现循环,但平台做的每一样东西,都是在给这个循环提供工具和上下文。弄懂它,才能看明白 Claude Code 排查时每一步在做什么,也才能判断一份工具说明或排查说明写得好不好。

**我的意见。**

## 模块 2:插件

**先读。** [09-插件形态](09-插件形态-原理与设计.md) 第 1 至 5 节、第 8 节。

**要弄懂。**

- [ ] 入口说明里没有只属于某个业务的内容

## 模块 3:登录授权

**先读。** [09-插件形态](09-插件形态-原理与设计.md) 第 6 节;[13-数据定义](13-数据定义-原理与设计.md) 第 3 节。

**要弄懂。**

- 公司 SSO、平台的 OAuth 页、网关,各管什么。有了 SSO 为什么还需要 OAuth 页。
- 登录 Claude Code 的账号和登录本平台是两回事。
- 身份接口只回答“你是谁”,不判断权限。
- 评估脚本为什么不能走浏览器登录,用什么代替。

**评审时看。**

- [ ] 第一次调用时浏览器自动弹出登录;登录后不需要复制粘贴任何东西
- [ ] 通行证过期后自动续期,同事无感知
- [ ] 没登录、通行证过期、通行证被撤销,都被拒绝
- [ ] 插件仓库、对话记录、审计里都搜不到通行证
- [ ] 开发用的假身份在测试和生产环境里不存在

**我的意见。**

## 模块 5:业务包的检查、编译和加载

**先读。** [11-业务包接入协议](11-业务包接入协议-原理与设计.md) 第 1 至 3 节、第 7 至 9 节;[14-生产化与部署](14-生产化与部署-原理与设计.md) 第 4 节;[13-数据定义](13-数据定义-原理与设计.md) 第 1、2 节。

**要弄懂。**

- 业务包在 Git 里是文件夹,网关运行时为什么不依赖文件夹。
- 文件里放什么,数据库里放什么。
- 改了一份排查说明,它是怎么到达每个网关副本的。怎么回滚。
- 检查命令查哪几类规则。

**评审时看。**

- [ ] 一个合规的样例通过;每个故意写错的样例都被指出错在哪

- [ ] 样例里混进一个密码时检查不通过
- [ ] 编译出的登记表符合文档 13 第 2 节的结构
- [ ] 把“当前版本”指回上一个,网关在一个轮询间隔内用回旧内容

## 模块 6:工具执行框架

**先读。** [11-业务包接入协议](11-业务包接入协议-原理与设计.md) 第 4 节;[13-数据定义](13-数据定义-原理与设计.md) 第 5 节;[14-生产化与部署](14-生产化与部署-原理与设计.md) 第 5 节。

**要弄懂。**

- 三种执行方式各适合什么;内置工具怎么挂进来。
- 工具的说明为什么算提示词的一部分。
- 结果的四种状态;`empty` 和 `error` 混在一起的后果。
- 所有工具都是只读的,为什么还需要限流和熔断。
- 它和代码服务的边界。

**评审时看。**

- [ ] 样例里的查询工具能查到测试库的数据
- [ ] 参数只能作为值填进查询;用参数去改变语句结构的尝试不成功
- [ ] 查一个不存在的记录返回 `empty`;把数据库连接弄断返回 `error`
- [ ] 超时的查询被中断;超过行数的结果被截断并说明总数
- [ ] `mask` 里的字段在返回里已脱敏
- [ ] 并发超过上限时被限流;数据源连续出错后被熔断,并且返回的是 `error`
- [ ] 新增一个只用配置的工具,不需要改代码

**我的意见。**

## 模块 7:业务包内容

**先读。** [11-业务包接入协议](11-业务包接入协议-原理与设计.md) 第 4 至 6 节;[从这里开始](00-从这里开始.md) 第 4 节。

**要弄懂。**

- 同一条信息只写一处:单个工具的用法写在工具说明里;一类问题怎么查写在排查说明里;所有任务都遵守的规则写在服务说明和入口说明里。
- 排查说明写思路和判断标准,不写死步骤;必须写清“查到什么程度才能下结论”。
- 服务地图按业务流程写:一条链路经过哪些服务、每一段靠什么关联、每一段成功的标志是什么。
- 排查说明的 `when` 决定它会不会被取用。
- 说明写得再好也只是建议。不能被违反的要求由平台强制。

**评审时看。**

- [ ] 两个业务包通过检查命令
- [ ] 每个工具的说明里写了“什么时候用”
- [ ] 服务地图里每一段都写了成功的标志,并且这个标志在日志或数据里确实查得到
- [ ] 把服务地图给一位不熟悉这条链路的同事看,他能看懂
- [ ] 表结构说明里每个状态字段的取值都有解释
- [ ] 说明里没有考题中的具体数据
- [ ] 公共包里没有只属于用户、会员、权益的内容
- [ ] 用十种不同的问法提问,数一数它有几次先取了排查说明

**我的意见。**

## 模块 8:代码服务

**先读。** [10-代码查询](10-代码查询-原理与设计.md) 全文。仓库怎么拉取和按版本存放,可参考 `参考` 目录里的《代码仓库管理》第 1、3.1 节。

**要弄懂。**

- 模型没有“学会”仓库,它是每次现查。

- 排查说明、导航、代码原文,各放在哪里。

**评审时看。** 文档 10 第 8 节各步的验收。重点:读不到快照之外的文件;代码证据带提交号;线上版本查不到时明确说明。

**自测。** 文档 10 第 12 节。

**我的意见。**

## 模块 9:评估

**先读。** [02-评估系统](02-评估系统-原理与设计.md) 第一部分;[09-插件形态](09-插件形态-原理与设计.md) 第 6.5、10 节。

**要弄懂。**

- 评估的对象是整个系统,不只是模型。
- 判的是结果,不是路线。
- 成对出题:有“应该先问”的题,也要有“不应该再问”的题。
- 案例少的时候通过率没有意义,这个阶段的产出是“每道错题错在哪”。
- 判断标准要在运行之前写好。

**评审时看。**

- [ ] 每道题的标准答案和评分要点是我自己写的,并且在运行之前写好
- [ ] 评分要点里没有规定排查路线的条目
- [ ] 评估用的是和同事相同的插件,通过同一个网关
- [ ] 评估用专用的服务令牌,在审计里能和真人区分
- [ ] 每次运行保存了 Claude Code 的版本、模型、登记表的版本
- [ ] 保存了完整过程,能看到每一步调用了什么工具
- [ ] 可以把任意两次运行逐题对比

**我的意见。**

## 持续:迭代方法

**先读。** [02-评估系统](02-评估系统-原理与设计.md) 第 5 至 8 节。

**要弄懂。**

- 失败案例比分数重要。分数说明好不好,失败案例说明该改什么。
- 每个失败归入一类,不同的类对应不同的改法:

| 失败类型 | 改哪里 |
| --- | --- |
| 缺少工具 | 业务包里增加工具 |
| 选错工具或参数填错 | 工具的名称、说明、参数 |
| 工具返回看不懂或太大 | 工具返回的字段和上限 |
| 找不到资料 | 仓库导航、表结构说明 |
| 排查说明没被取用 | 排查说明的 `when`;服务说明里的目录 |
| 排查说明指引有误 | 排查说明的正文 |
| 证据齐全但推理错误 | 排查说明中的判断标准 |
| 过早下结论 | 排查说明里“查到什么程度才能下结论” |
| 没有先提问 | 服务说明和入口说明里的规则 |

- 一次只改一样东西。
- 改动针对一类问题,不针对某一道题。
- 读完整的过程,不要只读最终的回答。
- 每次改动留一条记录。

**评审时看。**

- [ ] 每个失败案例都有归类,归类是我读过完整过程之后给出的
- [ ] 每轮的改动只有一项,针对的是占比最大的那类失败
- [ ] 每次改动后重跑了全部考题
- [ ] 有一份持续更新的改动记录

**我的意见。**

## 一期结束时

把各模块的“我的意见”汇总,再加上三项整体意见:

- 对架构的意见:哪些部分实现起来别扭,哪些划分不合理。
- 对安装、登录和使用体验的意见。
- 最想在二期做的事。

这些连同评估数据和试用数据,就是 [一期二期规划](一期二期规划.md) 第 4 节评审的输入。
