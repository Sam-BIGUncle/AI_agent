# 一期二期规划

一期做出一个能用的端到端系统:团队内的同事可以在网页上向它提问,它能回答三个基础服务的业务逻辑问题和具体用户的排查问题。一期只使用 Claude Agent SDK 作为运行时,连接器全部默认加载。二期有两项已经确定:自研运行时、使用方选择连接器;其余范围在一期结束时结合你的意见和一期积累的数据确定。

本文档是实现计划的唯一依据。框架见 [架构总览](架构总览.md),一期各部分的学习和评审见 [一期学习手册](一期学习手册.md)。

## 1. 两期的分工

| | 一期 | 二期 |
| --- | --- | --- |
| 目标 | 框架搭好,主流程跑通,小范围可用 | 自研运行时、平台化、能力深化、扩大使用范围 |
| 判断标准 | 能用,结构正确,每一部分你都理解 | 由一期的数据和你的意见决定 |
| 范围 | 本文档第 2 节,现在确定 | 第 5 节两项已确定,第 6 节是候选,一期评审后确定 |
| 原则 | 每个组件做最简单但结构正确的版本 | 在一期的框架内加厚或替换,不推倒重来 |

一期所有的取舍遵循一条规则:**框架级的东西一次做对,框架内的东西先做简单。** 框架级的东西指五层划分、四个接口、信任边界、连接器目录结构、所有变更经评估。二期的功能一期不实现,但一期的接口、目录和数据字段要为它们留好位置,具体见 [架构总览](架构总览.md)第 10 节。

## 2. 一期范围

### 2.1 做什么

| 部分 | 一期内容 |
| --- | --- |
| 问题类型 | 规则解释与接入(“某某业务逻辑是什么”);针对具体用户的排查(“我付费了,权益为什么没加上”) |
| 覆盖业务 | 用户、会员、权益三个服务 |
| 对话页面 | 流式显示回答;排查过程可折叠查看;结论卡片;渲染 Markdown 和 Mermaid;历史对话;有用或无用的反馈;显示当前加载的连接器和使用的运行时(只显示,不可选) |
| Agent 服务 | 对话与任务管理;任务信息注入;通过运行时接口调用运行时;保存轨迹;基础的多轮对话 |
| 运行时接口 | 用 proto 定义;事件流。接口不含任何 SDK 特有的内容 |
| 运行时 | 只有 Claude Agent SDK 的适配这一个实现 |
| MCP 网关 | 日志查询(ClickHouse)、业务数据只读查询(MySQL 从库)、缓存读取(Redis)、最近的发布记录;身份校验;审计;结果大小限制 |
| 连接器内容 | 两个连接器目录:公共连接器(日志、发布记录、通用排查方法)和基础业务连接器(用户、会员、权益)。基础业务连接器是一个,内部按服务分组,可以包含多个 MCP 工具和多个 Skill。全部默认加载 |
| 代码目录 | 多个仓库放在同一个任务目录下;用脚本更新;可指定版本 |
| 评估 | 案例文件;批量运行;人工判断;记录每一个真实提问 |
| 安全 | 真实登录,操作记到人;运行时在不持有凭据的隔离环境中运行;全部只读;前端不加载外部资源 |

### 2.2 不做什么

下列内容一期不做。一期的设计为它们留了位置,但不实现。

| 不做 | 一期的替代做法 | 归属 |
| --- | --- | --- |
| 自研运行时、运行时切换 | 只用 SDK 运行时;运行时接口照常定义,运行时通过一张只有一项的注册表配置 | 二期已确定 |
| 使用方选择连接器 | 两个连接器全部默认加载,界面只显示 | 二期已确定 |
| 整体异常排查(“失败率为什么升高”) | 可以尝试,但不作为验收内容 | 二期候选 |
| 业务方接入、注册表、生命周期管理 | 只有平台自己的两个连接器目录 | 二期候选 |
| 按应用的细粒度授权 | 白名单内的用户可以访问三个服务的数据 | 二期候选 |
| 代码按线上版本自动准备、仓库自动同步 | 脚本更新,默认使用主干,可手动指定版本 | 二期候选 |
| 轮次边界压缩、会话摘要 | 使用 SDK 自带的会话接续和压缩 | 二期候选 |
| 检索与记忆 | 文档放在目录里,由 Agent 搜索阅读 | 二期候选 |
| 截图与文件上传 | 只支持文字输入;接口按内容块定义 | 二期候选 |
| 模型网关、模型路由 | 运行时直接调用模型 | 二期候选 |
| 自动判分、评估数据冻结 | 人工判断,直接查询线上数据 | 二期候选 |
| 对比视图、链路视图 | 排查结果用文字和 Mermaid 表达 | 二期候选 |
| IM 机器人、本地插件、报警自动触发 | 只有网页入口 | 二期候选 |
| 子 Agent、多 Agent、沙箱、其他框架的运行时 | 不涉及 | 二期候选 |
| 任何写操作 | 不涉及 | 二期候选 |

## 3. 一期的里程碑

```mermaid
flowchart LR
  M0["M0 准备"] --> M1["M1 骨架打通"] --> M2["M2 能力加厚"] --> M3["M3 多轮与体验"] --> M4["M4 安全与试用"] --> M5["M5 一期评审"]
  M5 --> P2["二期"]
```

| 里程碑 | 内容 | 完成标志 | 对应学习单元 |
| --- | --- | --- | --- |
| M0 准备 | 用现有的 CLI 手工问 5 个常见问题并记录;整理手上的常见问题,写出参考答案;开始记录每一个真实提问;申请 ClickHouse、MySQL 从库、Redis 的只读账号;写出服务地图初稿 | 一批案例文件;各数据源的只读访问已开通 | 1、2、4 |
| M1 骨架打通 | 对话页面、Agent 服务、运行时接口、SDK 运行时、MCP 网关各做最薄的版本,网关只有日志查询一个工具;评估脚本通过对话接口批量运行 | 在页面上问一个业务逻辑问题和一个需要查日志的问题,都能得到回答;评估脚本能跑完全部案例并输出结果表 | 3、5、6、9 |
| M2 能力加厚 | 网关增加业务数据、缓存、发布记录的工具;完成两个连接器的内容:常驻说明、服务地图、排查说明、表结构说明、仓库说明;多仓库的代码目录;开始每周的改进循环 | “付费后权益未到账”这类问题能沿链路逐段确认并给出带证据的结论;缺少用户标识时会先提问 | 3、4、10、11 |
| M3 多轮与体验 | 多轮对话、轮次信息注入、历史对话;结论卡片;反馈;界面打磨 | 能追问;不懂技术的同事能看懂结论;界面达到预期的观感 | 7、9 |
| M4 安全与试用 | 登录;审计记到人;运行时隔离;前端外部资源限制;请两三位同事试用一到两周 | 试用期间无越权和数据外泄问题;收集到真实的使用记录和反馈 | 8 |
| M5 一期评审 | 汇总数据;你逐个单元提出意见;确定二期范围 | 一份一期总结和二期范围 | 全部 |

学习单元 2(Agent 循环)在一期只学习、不实现。它讲的是整个系统的核心原理,放在 M0 学,有助于理解之后 SDK 运行时的行为。

每个里程碑结束时做三件事:重跑评估并保存结果;在学习手册对应的单元里完成评审清单;记下你的疑问和意见。

## 4. 一期评审

一期结束时,二期的范围由三类输入决定。

| 输入 | 内容 |
| --- | --- |
| 你的意见 | 学习手册每个单元末尾的“我的意见”;对整体架构、界面、使用体验的意见 |
| 评估数据 | 各类问题的结果;失败案例的分类及占比 |
| 使用数据 | 试用期间的真实提问;反馈为无用的回答;每次任务的耗时和费用;同事提出的需求 |

评审时逐项回答:

- 哪类问题答得好,哪类答得差?差的主要原因是缺工具、缺说明、缺资料,还是推理错误?
- 同事实际问的问题,和一期设定的两类问题一致吗?
- 单次任务的成本和耗时是否可以接受?
- 架构中哪些部分在实现时感到别扭,需要调整?
- 为二期预留的位置,在一期的实现中是否都保持了?

二期范围等于:第 5 节已确定的两项,加上本节得出的改进项,加上第 6 节候选清单中被数据支持的项。

## 5. 二期已确定的两项

### 5.1 自研运行时

| 项目 | 内容 |
| --- | --- |
| 是什么 | 自己实现的 Agent 循环,与 SDK 运行时实现同一个运行时接口 |
| 目的 | 掌握运行时的实现;在成本或合规要求变化时有可替换的方案 |
| 做法 | 按 [自研运行时:原理与设计](03-自研运行时-原理与设计.md)第 8 节分步实现:先做到能参加评估,再逐项追近 SDK。每一步都在同一批案例上与 SDK 对比 |
| 带来的平台功能 | 运行时注册表增加一项;页面上可以选择 Agent;同一个问题可以交给两个运行时对比;评估可以指定运行时 |
| 上线条件 | 先只参加评估;之后对白名单用户以“实验”状态开放;评估结果不低于 SDK 后才考虑成为可选的正式运行时 |
| 一期为它做的准备 | 运行时接口不含 SDK 特有的内容;Agent 服务通过注册表调用运行时;任务记录中保存运行时的名称和版本;评估程序把运行时作为参数;前端按统一的事件渲染 |
| 一期的学习 | 学习手册单元 2 讲循环的原理,单元 5 讲接口 |

方案细节:文档 03 全文;文档 01 第 4.5、4.6 节;文档 06 第 8 节。

### 5.2 使用方选择连接器

| 项目 | 内容 |
| --- | --- |
| 是什么 | 使用方在一次对话中决定启用哪些连接器;业务方可以把自己的业务做成连接器接入 |
| 三类连接器 | 公共连接器始终加载;基础业务连接器默认加载;其他业务连接器由使用方选择后加载 |
| 选择方式 | 手动选择;团队默认;Agent 在排查中建议启用,由使用方确认 |
| 连接器的形态 | 工具型(只有 MCP 工具)、说明型(只有 Skill)、业务型(工具、Skill、知识、仓库、案例齐备)。可以单独配置一个 MCP 或一个 Skill |
| 范围 | 个人、团队、平台 |
| 隔离 | 一次对话只使用它加载的连接器。未加载的连接器的工具、Skill、知识、代码都不进入这次对话,业务之间互不干扰 |
| 一期为它做的准备 | 内容从第一天就按连接器目录组织,分为公共和基础业务两个;每个连接器有清单文件;工具名带前缀;平台的常驻说明里不放业务特有的内容,业务规则放在连接器自己的说明里;任务记录中保存加载了哪些连接器;对话接口中保留“本次对话启用的连接器”字段,一期由服务端填默认值;界面上显示当前加载的连接器 |

方案细节:文档 04 第 2.2、6、7.1 节;文档 05 第 2、3.4 节。

## 6. 二期候选

以下不是承诺。排序和取舍在一期评审时决定。

| 方向 | 候选内容 | 什么数据支持做它 | 细节在 |
| --- | --- | --- | --- |
| 平台化 | 业务方接入连接器的完整流程;注册表与发布流程;工具和 Skill 的生命周期;个人和团队范围 | 有第二个业务想接入;同事想添加自己的工具或说明 | 文档 04、05 |
| 权限与生产化 | 按应用的细粒度授权;群对话的权限范围;成本上限与统计 | 使用范围扩大到三个服务的团队之外 | 文档 01 第 11、13 节 |
| 代码版本 | 按线上版本准备代码;仓库自动同步;公共库版本推导 | 出现“代码与线上不一致导致答错”的案例 | 文档 08 |
| 上下文与多轮 | 轮次边界压缩;固定区;会话摘要;话题切换提示 | 长对话的成本偏高或后段质量下降 | 文档 06 |
| 检索与记忆 | 排查经验的检索;受控的记忆 | 失败案例中“找不到资料”占比高;同类问题反复出现 | 文档 01 第 4.8 节 |
| 多模态 | 截图与文件上传;工具返回图片;生成图表 | 同事反复想发截图 | 文档 07 |
| 更多问题类型 | 整体异常排查;监控工具;报警自动触发排查 | 同事实际在问这类问题 | 文档 01 第 10 节 |
| 评估深化 | 自动判分与校准;评估数据冻结;留出集;发布门禁 | 案例积累到三十个以上;人工判断成为负担 | 文档 02 |
| 模型与成本 | 模型网关;模型路由与降级;缓存优化 | 成本成为问题;需要使用多个模型 | 文档 01 第 4.7 节 |
| 界面 | 对比视图;链路视图;生成式界面 | 一期界面使用后的意见 | 架构总览第 6 节 |
| 更多入口 | IM 机器人;本地 Claude Code 插件 | 同事希望在其他地方使用 | 文档 05 |
| 子 Agent 与多 Agent | 子 Agent 用于隔离占用上下文的工作;多 Agent 作为与单 Agent 的对比实验 | 出现上下文被大量日志占满的案例 | 文档 01 第 4.3、4.8 节 |
| 其他实验 | 沙箱;其他框架的运行时;检查点恢复 | 学习目的,各限时完成 | 文档 01 第 4.8 节 |
| 受控写操作 | 重新处理消息、补发权益等,带人工确认 | 排查结论稳定可靠,且同事希望一步到位 | 文档 01 第 11.4 节 |
